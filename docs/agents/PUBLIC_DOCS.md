# Public documentation, examples and CI — checkpoint policy

**Goal:** A visitor to the **currently published branch** can start at GitHub's root `README.md`, follow links to supported setup/reference/example instructions, and build/run **Hazelnut** and **Nutella** with the tracked example projects on each *documented supported platform*. Documentation describes the actually verified state, not planned capabilities. Experimental branches may temporarily fail these expectations: disclose the stage and deferred gates; don't manufacture a passing result.

## Authority and scope

- Current source, checked-in scripts, Premake, workflow YAML, examples, actual CI runs and native test evidence outrank prose. Verify the **branch and SHA** before claiming status. A passing result from master is not proof that `feature/3d-foundations` passes; a manual branch workflow dispatch is not a push-triggered check.
- Public-facing entry points currently include `README.md` → `docs/README.md`, `docs/getting-started.md`, `docs/development.md`, `docs/platforms-and-dependencies.md`, `docs/packaging.md`, `docs/editor-guide.md`, `docs/scripting.md`, `CONTRIBUTING.md`, example project READMEs and their links; follow any further links that contain active instructions. `docs/design/` holds historical investigation/qualification records, which should remain attributable to their actual revision rather than being rewritten as evergreen product guides.
- Keep the root README useful at a glance: what Hazel/Hazelnut/Nutella do, **implemented** features, platform requirements, clone/build/run/first-example paths, genuine screenshots, current status/limitations, CI badges and navigable docs links. Prefer a concise entry point over repeating full platform guides.

## When to update (not on every prompt)

**Same change or nearest stable checkpoint:** public CLI/flags/dependencies, prerequisite or minimum OS/toolchain changes, supported feature/format behavior, user-facing editor/player workflows, example scenes/projects, new screenshots needed to represent changed UI, packaging/export, platform support or CI workflow changes. Fix affected guide text and upstream links; do not rewrite all docs for a minor source edit.

**At each integrated milestone or before a release/public demonstration, and periodically after substantial feature batches:** perform a *public-docs health pass* using `hazel-public-docs`. Trace `README.md` outward through links, validate clone/setup/build/run/example/export instructions and CI claims. A checkpoint can be explicitly requested as a docs-only task; it must not silently authorize implementation, dependency upgrades, commits, releases or workflow dispatches.

**During incomplete experiments, unqualified renderer work or environment blockers:** preserve the engineering record; note public-docs changes needed and the checkpoint that will trigger them. Do **not** force a clean build, screenshots, full multiplatform test matrix or unsupported feature claims merely to keep interim edits green. If a branch is knowingly nonfunctional, document that conspicuously where visitors will encounter instructions; don't claim green based on earlier SHA.

## Audit checklist at a public checkpoint

1. **Branch-aware start:** From the branch being published, verify commands as written. A default `git clone` checks out the repository default branch, not the feature branch. Where telling readers how to test current development, provide a correct `git clone --branch <current-branch> --recurse-submodules ...` or branch-switch sequence, with clear distinction from `master`. Do not hardcode a development branch as a permanent universal default. Link to exact paths that exist at that branch; initialize pinned submodules, not `--remote`.
2. **Platform matrix:** Cross-check Windows (documented MSVC/PowerShell), maintained Linux (Ubuntu baseline/X11; optional Arch/CachyOS specifics) and Apple Silicon macOS against current `scripts/hazel.py`, `scripts/setup.*`, toolchain pins, Premake and actual jobs. Each supported platform needs clear prerequisites, configuration, how to build and launch Hazelnut, how to build/run Nutella with an example, and applicable shader/script/package preparation. Explicitly state known gaps, platform-only Metal features and unavailable runtimes. Avoid implying every arbitrary OS/distribution is supported.
3. **Examples:** Verify README project paths, `*.hproj`, scene names, script modules, assets, selected sample commands, and whether each example can be opened by Hazelnut and played/run by Nutella; cover authoring versus packaged/source-free run expectations. No destructive tests on owner's projects. Update linked example guides when controls, screenshots or outcomes change.
4. **Screenshots/media:** Confirm image files exist, relative paths resolve, labels/alt text describe actual content, and images reflect currently demonstrated features. Refresh on significant visual changes **only with a real captured and representative editor/player image**. Never fabricate a screenshot, claim it came from native hardware without capture evidence, or silently keep an obsolete screenshot as current; label historical screenshots if intentionally retained. Avoid screenshot churn during a WIP.
5. **Links and claims:** At a checkpoint first run `python3 tools/agents/check_public_docs.py --root .` for tracked-like local links/images reachable from the root README. This is a fast static screen, not a full GitHub anchor/external-link or human command validation; correct its genuine findings before manual review. Walk first-level and relevant downstream internal Markdown links, case-sensitive paths and anchors (including from examples and back into docs). Check commands from their target contexts, cross-platform syntax, linked external prerequisites when changing them, and clearly distinguish *implemented*, *experimental*, *qualified*, *planned*, and *unsupported* features. Avoid copied stale commit/results tables.
6. **CI/badges:** Inspect `.github/workflows/` and its trigger policy. Keep README badge links aligned with real workflow names and intended branch; label master status separately from feature-branch status. For this repo the canonical workflow is `.github/workflows/c-cpp.yml`; topic pushes alone need not run CI because the workflow targets master pushes, PRs and manual dispatch. Do not manufacture branch success, silently change CI triggers, break existing Windows/Linux/macOS jobs, or use hosted macOS build evidence as native Apple GPU validation. If a branch run is needed, request authorization for a PR/dispatch and report unverified until it actually runs.
7. **Evidence:** Use the smallest representative clean-checkout verification available locally; rely on recorded CI only for the **same SHA** and jobs actually run. At a milestone/release checkpoint seek relevant Debug/Release, examples, editor/player smoke, source-free relocation/export and platform tests, recording PASS / FAIL / NOT RUN / BLOCKED by OS and workload. Local-only tests do not support universal build claims.

## Reporting and keeping cost bounded

- For a scoped public behavior change, report `docs updated` or `docs deferred` (why, proposed checkpoint); don't perform a full link audit unless requested or at checkpoint.
- For a public-docs checkpoint, give a brief drift table (path, factual correction, evidence), changed files, link/command checks, CI status per branch/platform and unresolved hardware/gates. Prefer links to retained evidence over verbose pasted logs.
- Fix factual drift and broken navigation before polishing prose. Keep screenshots selective, don't rerun a full test suite merely to reword docs, and avoid recurring scans when no public behavior changed.
- Existing docs are user-facing; `docs/agents/` and `AGENTS.md` are **instructions for Codex**, not substitutes for the public getting-started guides.
